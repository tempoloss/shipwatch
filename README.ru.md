# shipwatch

Доводит до конца публичную часть релиза.

[English version](README.md)

Не хранилище задач. Не напоминалки. Не чат-бот. Одна работа: когда что-то
изменилось — произвести то продолжение, которое иначе забывается.

- **Ты ставишь тег релиза** → в этом же репозитории появляется issue с чеклистом
  публичной части, а в Telegram приходит ссылка на него.
- **ISO 20022 публикует новую версию сообщения** → issue появляется в
  `quackiso` с тем, какое сообщение сдвинулось и что проверить.

Работает на GitHub Actions. Без сервера, без хостинга, бесплатно.

## Почему issue, а не список задач

Открытый issue рядом с кодом выглядит незакрытым. В этом весь механизм. Помнить
не надо ничего, потому что каждый триггер — это событие, которое уже случилось.

## Почему так

| решение | почему | детали |
|---|---|---|
| Напоминание — это открытый issue | видно, что не закрыто, лежит рядом с кодом, и помнить не надо | [ADR 0001](docs/adr/0001-an-open-issue-is-the-reminder.md) |
| Новый тег и новая версия ISO — одна задача | и то и другое это «сравни реальность с тем, что видели в прошлый раз», значит один раннер и подключаемые вотчеры | [ADR 0002](docs/adr/0002-one-mechanism-two-watchers.md) |
| GitHub Actions, а не сервер | нет всегда включённого железа, и нет машины, где уместно держать доступы | [ADR 0003](docs/adr/0003-github-actions-not-a-server.md) |
| Состояние пишется только после того, как все синки приняли | «хотя бы один раз» лучше тихой потери, дубль восстановим | [ADR 0004](docs/adr/0004-state-is-written-only-after-delivery.md) |
| Первая встреча усыновляется молча | иначе первый прогон заводит issue на каждый исторический тег сразу | [ADR 0005](docs/adr/0005-adopt-on-first-sight.md) |
| Два токена GitHub | `GITHUB_TOKEN` не может открыть issue в другом репозитории | [ADR 0006](docs/adr/0006-two-github-tokens.md) |
| Heartbeat пишет, что произошло | он не может ничего заглушить, и он держит расписание включённым | [ADR 0007](docs/adr/0007-the-heartbeat-records-what-happened.md) |
| Архивный снимок лучше тишины | в чужом снимке может лежать версия, которой мы не видели, в своём кэше — нет | [ADR 0008](docs/adr/0008-an-archived-snapshot-beats-silence.md) |

## Установка

**1. Узнай chat id в Telegram.** Сначала напиши боту *сам* — `getUpdates` пустой,
пока не напишешь, и бот не может написать тебе первым.

```
https://api.telegram.org/bot<TOKEN>/getUpdates
```

Возьми `result[0].message.chat.id`.

**2. Создай fine-grained personal access token.** `GITHUB_TOKEN` заперт в том
репозитории, где идёт workflow: он прочитает публичные репы, но **не сможет**
открыть issue в `tempoloss/quackiso` из `tempoloss/shipwatch`. Токену нужен
**Issues: write** на каждый наблюдаемый репозиторий.

**3. Добавь секреты репозитория** (Settings → Secrets and variables → Actions):

| секрет | значение |
|---|---|
| `GH_PAT` | токен из шага 2 |
| `TELEGRAM_TOKEN` | токен бота от `@BotFather` |
| `TELEGRAM_CHAT_ID` | id из шага 1 |
| `HEALTHCHECK_URL` | *по желанию, но лучше с ним* — бесплатный ping-URL с healthchecks.io |

`HEALTHCHECK_URL` превращает живость в событие вместо отсутствия, которое надо
самому заметить. Поставь ему период ожидания в два интервала: запуски по
расписанию у GitHub делаются по возможности, и один задержавшийся прогон —
норма. Без него тихо отключённое расписание выглядит ровно как спокойная неделя,
а расписание, отключённое за неактивность, **само не восстанавливается**.

Токен бота не коммитить никогда. GitHub сканирует публичные репозитории на
секреты, сообщает об утёкших токенах Telegram наверх, и Telegram их отзывает —
так что закоммиченный токен даёт молча мёртвого бота.

**4. Запушь, потом один раз запусти workflow вручную** (Actions → watch → Run
workflow). Первый прогон **усыновляет**: записывает все существующие теги и
версии, *ничего не анонсируя*. Без этого первый прогон завёл бы issue на каждый
исторический релиз разом.

**5. Убедись, что живой.** Должен появиться коммит `state:`. Этот коммит —
одновременно доказательство живости и то, что не даёт отключить расписание.

## Настройка

`config.json`:

- `repos` — за какими репозиториями следить на новые теги
- `iso_families` — сообщения ISO 20022, которые реализует quackiso
- `iso_issue_repo` — куда заводить issue по ISO
- `intervals_hours` — `tags` 20 ч, `iso` 168 ч

Всё крутит одно ежедневное расписание, а каждый вотчер сам решает, пришло ли его
время. Так частота живёт в одном обозримом файле, а не в нескольких строках
cron.

ISO — раз в неделю намеренно. Источник не просто лимитирует запросы, он
недоступен большую часть времени: замерено 2026-08-03, он ответил один раз за
1,7 с и отдал 122 идентификатора, а потом отвалился по таймауту на трёх
повторах подряд. ISO выпускает maintenance-релизы раз в год, так что опрос раз в
6 часов — это ~1460 запросов, чтобы поймать одно событие.

Поскольку живая страница обычно не отвечает, загрузка идёт водопадом: одна
попытка к `iso20022.org`, потом самый свежий снимок из Wayback Machine. Снимок
старше 180 дней отвергается, а в дайджест печатается `live` или
`archive (2026-05-13)`, чтобы успешную проверку нельзя было спутать с живой.

## Правило, вокруг которого всё построено

> **Состояние не пишется, пока не удались и загрузка, и разбор, и не сдвигается
> для события, пока его не принял каждый синк.**

Важны обе половины. Если таймаут дал пустой результат и его бы сохранили, все
сообщения оказались бы помечены как уже виденные, и монитор навсегда замолчал
бы, продолжая отчитываться об успехе. А если состояние закоммитить до того, как
синк упал, событие никогда не будет отправлено заново — при том, что файл
состояния утверждает обратное.

Это тот же класс отказа, что `NULL`, который тихо выпадает из `SUM`: неверно,
беззвучно и вызывает доверие.

Значит, доставка — **хотя бы один раз**. Дубль восстановим, тихая потеря нет. У
каждого события детерминированный ключ, и синк issue проверяет его перед тем,
как заводить новый.

Гарантии структурные, а не договорные:

- вотчеры кидают `ParseError` вместо того, чтобы вернуть пустоту
- **записи — монотонное слияние**: состояние только добавляет тег или поднимает
  версию, так что недорисованная страница даёт пустую операцию, а не удаление
  ключа с последующим молчаливым повторным усыновлением
- ISO-вотчер отвергает страницу, где меньше 100 идентификаторов или меньше 3
  бизнес-областей — это ловит и длинную страницу ошибки, и тонкую
- ключ состояния — `area.message`, никогда одна бизнес-область: `camt.003` и
  `camt.053` версионируются независимо
- группа версии — `\d{2,}`: фиксированные `\d{2}` заставили бы сообщение версии
  100 исчезнуть из разбора и замереть навсегда
- граница — по каждой цели: один упавший репозиторий не может пересеять соседей
- версия, поехавшая назад, оставляет более высокое записанное значение
- недоставленное событие блокирует запись состояния, поэтому повторится

Heartbeat — одно намеренное исключение: он записывает, что *произошло*, а не что
*увидели*, поэтому заглушить ничего не может, и коммитится с `if: always()`,
чтобы падение всё равно его оставило.

## Тесты

```
python -m unittest discover -s tests
```

38 тестов, без сети. Вотчеры разделены на `fetch` (грязный) и `parse` (чистый),
поэтому каждый путь разбора проверяем. Большинство тестов защищает правило выше,
а не happy path. Тесты раннера существуют потому, что однажды отсутствующий
секрет прервал `main` до записи heartbeat, а шаг коммита с `always()` затем умер
на отсутствующем `state/`: механизм, написанный чтобы пережить падение, был
убит падением. Тесты загрузки закрепляют обе стороны порога свежести снимка —
единственного, что отличает полезный архив от протухшего.

## Известные ограничения

- Идентификаторы версий читаются из HTML страницы. Редизайн это ломает —
  громко, через порог правдоподобия, а не тихим «изменений нет».
- «Самая высокая версия, встреченная на странице» — эвристика, её можно обмануть
  версиями из истории изменений или примеров.
- Префиксы бизнес-областей в регулярке — фиксированный список. Сообщение вне
  него не отслеживается; недельный дайджест сообщает, сколько настроенных
  сообщений нашлось, так что дырка видна, а не беззвучна.
- Архивный фолбэк освежается только если кто-то архивирует страницу. Если никто
  не архивирует, а живой источник лежит, снимок старится до порога 180 дней и
  отвергается — тогда ISO падает громко, и вернуться некуда, кроме как ждать
  восстановления живого источника.
